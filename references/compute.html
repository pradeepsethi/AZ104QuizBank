1. Compute Domain Scope

The guide's Azure services section identifies Compute as the processing power required by applications and systems to perform computational tasks. Services listed there include Virtual Machine, App Service, Functions, and Kubernetes Service.

Compute topics covered in this guide: ARM Templates & Bicep, Azure Virtual Machines, Disk Encryption, VM Scale Sets, Availability Zones/Sets, VM Disks, Azure Container Registry, Azure Container Instances, Azure Container Apps, and Azure App Service (plans, scaling, certificates/TLS, custom domains, backup, networking, deployment slots).

2. ARM Templates & Bicep

What They Are

  • ARM template: A JSON file that defines the infrastructure and configuration for a deployment declaratively. Core sections: parameters, variables, resources, and outputs.
  • Bicep file: A domain-specific language (DSL) that transpiles to ARM JSON. Same capabilities as ARM templates but with simpler, more readable syntax — no need for nested "[resourceId(...)]" expression strings.

Interpreting a Template

Section Purpose
$schema / contentVersion Identifies the template language schema and version.
parameters Values supplied at deployment time (e.g. VM size, admin username).
variables Values computed/reused within the template to avoid repetition.
resources The actual Azure resources to deploy, each with a type, apiVersion, name, and properties.
outputs Values returned after deployment (e.g. a resulting resource ID or FQDN).

Modifying Templates

  • ARM JSON: Edit the relevant resources block directly, or add new parameters/variables as needed. Use dependsOn to control deployment order between dependent resources.
  • Bicep: Edit .bicep resource declarations (resource symbolicName 'type@apiVersion' = { ... }). Modules (module keyword) let you reference other Bicep files for reusable components.

Deployment

CLI: az deployment group create --resource-group <rg> --template-file main.bicep --parameters params.json
PowerShell: New-AzResourceGroupDeployment -ResourceGroupName <rg> -TemplateFile main.json
  • Deployment scopes: resource group, subscription, management group, or tenant.
  • Deployment modes: Incremental (default — adds/updates resources, leaves unreferenced resources untouched) vs Complete (deletes resources in the resource group not defined in the template).

Export & Convert

  • Export a deployment: In the Azure portal, a resource group's Deployments blade lets you export the template used for any prior deployment, or use Export template on the resource group itself to generate a template from its current state.
  • Convert ARM JSON → Bicep: az bicep decompile --file main.json
  • Convert Bicep → ARM JSON: az bicep build --file main.bicep

3. Azure Virtual Machines

Components and Creation Flow

  1. Subscription and resource group: Choose the subscription and resource group. A subscription is the container where Azure resources are provisioned; a resource group logically organizes resources.
  2. Availability: Choose Availability Zone, Availability Set, or no infrastructure redundancy option.
  3. Image: Contains the OS, settings, and applications.
  4. VM type and size: Determines physical properties such as vCPUs, RAM, and disks.
  5. Billing: Select Spot or another billing type such as pay-as-you-go or reserved.
  6. Access: Use a key pair; secure the public-key copy to preserve direct instance access.
  7. Storage: Add OS disk, data disk, and temporary disk.
  8. Networking: Select the virtual network and Network Security Group rules.
  9. Management: Enable monitoring, auto-shutdown, and backup.
  10. Advanced configuration: Add extensions, user data, or Proximity Placement Groups.
  11. Tags: Identify and classify resources.
  12. Deploy & Redeploy: Review configuration and launch. Redeploying moves the VM to a new node while retaining configuration.

VM Types

Type Guide Description / Use Cases
General Purpose Balanced CPU-to-memory ratio; testing, dev, low-to-medium traffic web servers. B-series provides burstable performance.
Compute Optimized High CPU-to-memory ratio; medium-traffic web servers, network appliances, batch processes, analytics.
Memory Optimized High memory-to-CPU ratio; relational databases, medium-to-large caches, in-memory analytics.
Storage Optimized High disk throughput and I/O; SQL/NoSQL databases, big data, data warehousing.
GPU Compute-intensive, graphics-intensive and visualization workloads.
High-performance compute Powerful/fast CPU and high-throughput network interfaces; fluid dynamics, weather modeling, seismic processing.

Azure Disk Encryption (ADE)

  • Encrypts OS and data disks inside the guest OS using industry-standard BitLocker (Windows) or DM-Crypt (Linux).
  • Encryption keys are safeguarded in an Azure Key Vault as secrets (and optionally a Key Encryption Key, KEK, for double-wrapping).
  • Different from (and can be layered with) Storage Service Encryption (SSE) / encryption at rest, which encrypts at the platform/storage layer and is enabled by default on all managed disks.
  • Not supported: Basic-tier VMs, and (at the time of writing) some generation-2/confidential VM combinations — check current support before enabling.
Exam tip: ADE = guest-OS-level encryption via BitLocker/DM-Crypt, keys in Key Vault. SSE = platform-level, on by default, no guest OS involvement.

Moving a VM

Move Type Guide Notes
Another resource group Supported for the VM and its associated resources (disks, NICs). Both source and target resource groups are locked during the move.
Another subscription Same move mechanism as resource groups; target subscription must have the required resource providers registered and be in the same Azure AD (Entra ID) tenant, or use Azure Lighthouse/manual recreation across tenants.
Another region Not a native "move" — done via Azure Resource Mover, or by recreating the VM from a snapshot/image/ARM template exported from the source region.

Managing VM Sizes

  • Resize via Portal → VM → Size, CLI (az vm resize), or PowerShell (Update-AzVM/-Size).
  • Resizing within the same hardware cluster only requires a reboot; resizing to a size not available on the current cluster requires deallocating (stop) the VM first.
  • Not all sizes are available in all regions/clusters — check az vm list-vm-resize-options before planning a resize.

Availability Zones vs Availability Sets

Option Guide Description
Availability Zone Physically separate datacenters within a region, each with independent power, cooling, and networking. Protects against datacenter-level failure. SLA up to 99.99%.
Availability Set Logical grouping within a single datacenter, spread across Fault Domains (shared power/network) and Update Domains (patched/rebooted together). Protects against rack-level hardware/maintenance failure. SLA 99.95%.

Virtual Machine Scale Sets (VMSS)

  • A group of identical, load-balanced VMs that can automatically increase or decrease instance count in response to demand or a defined schedule.
  • Scaling modes: manual (fixed instance count), custom autoscale (CPU/memory/metric-based rules), or predictive autoscale (forecasts load from historical patterns).
  • Orchestration modes: Uniform (identical instances from a single model, ideal for stateless workloads) vs Flexible (mix of VM sizes/configs, supports Availability Zones and closer parity with standalone VM features).
  • Integrates with Azure Load Balancer or Application Gateway to distribute traffic across instances.
  • Upgrade policy controls how instances receive model changes: Manual, Automatic, or Rolling (staged, with health-probe checks between batches).

4. Virtual Machine Disks

VM disks are block-level storage volumes managed by Azure and primarily used for Azure VMs.

Disk Roles

  • OS Disk: Required for a VM. Persistent OS disks preserve data when upgrading. Ephemeral OS disks offer lower latency for stateless workloads.
  • Data Disk: Stores application data. Can be created from snapshots, blobs, or empty disks.
  • Temporary Disk: Short-term storage for page/swap files. Data may be lost during redeployment.

Disk Types Comparison

5. Azure App Service

In App Service, an application always runs in an App Service plan, which defines the collection of compute resources for web, API, or mobile apps.

Creating an App

  • Choose a publish model: Code (with a language stack/runtime) or Docker Container (with a registry image).
  • Choose an OS (Windows or Linux) — this is fixed for the life of the App Service plan; you can't mix OS types on the same plan.
  • Select or create the App Service plan (region + tier determine cost and capability).

Configuring Scaling

Scaling Type Guide Description
Scale up (vertical) Change the App Service plan's pricing tier to get more CPU/RAM/features per instance. Causes a brief restart.
Scale out (horizontal) — manual Set a fixed instance count (subject to the tier's max instance limit).
Scale out — autoscale Define rules based on metrics (CPU %, memory, HTTP queue length) or a schedule; requires Standard tier or above.

Certificates & TLS

  • Certificate options: App Service Managed Certificate (free, auto-renewed, for a custom domain, no wildcard support), App Service Certificate (purchased through Azure, stored in Key Vault), or bring-your-own (upload a .pfx, or import from Key Vault).
  • TLS/SSL binding requires the app to be on a custom domain (not the default *.azurewebsites.net) except for SNI-based defaults.
  • TLS enforcement: "HTTPS Only" setting redirects all HTTP traffic to HTTPS; minimum TLS version is configurable per app.
  • Mutual TLS (mTLS): Can require client certificates for incoming requests.

Custom Domains

  • CNAME record: Maps a subdomain (e.g. www) to <app>.azurewebsites.net — simplest option, doesn't work for root/apex domains.
  • A record: Maps the root/apex domain directly to the app's inbound IP address.
  • TXT record: Used during domain verification (asuid record) to prove ownership.
  • Free tier plans cannot use custom domains — requires Shared tier or above.

Backup

  • Backs up app configuration, file content, and connected databases to an Azure Storage account/container.
  • Requires Standard tier or above; manual backups also available on Free/Shared with limits.
  • Supports scheduled (automatic, periodic) or on-demand backups; retention and frequency are configurable.
  • Restores can go to the same app or a different app/slot.

Networking Settings

  • VNet Integration: Lets the app reach resources inside a virtual network (outbound traffic); requires Standard tier or above.
  • Private Endpoint: Gives the app a private IP inside a VNet for inbound traffic, removing it from the public internet; requires Premium tier or above.
  • Access Restrictions: IP-based or service-endpoint-based allow/deny rules controlling who can reach the app.
  • Hybrid Connections: Lets the app reach specific on-premises TCP endpoints without a full VPN.

Deployment Slots

  • Live, separately-configurable versions of an app (e.g. staging) that share the same App Service plan resources.
  • Requires Standard tier or above (number of slots increases with tier).
  • Swap: Exchanges a slot's content/configuration with production with no downtime; some settings are "slot-specific" (e.g. connection strings can be pinned) and don't swap.
  • Useful for staged rollouts, canary testing, and instant rollback (swap back).

6. Azure Containers (ACR, ACI & Container Apps)

Azure Container Registry (ACR)

A private, managed Docker registry service for storing and managing container images and Helm charts close to your deployments.

Tier Guide Notes
Basic Cost-optimized entry point; lower storage/throughput — dev/test.
Standard Same features as Basic with more included storage and higher throughput for production workloads.
Premium Highest throughput; adds geo-replication, content trust/signing, private endpoints, and customer-managed keys.
  • Admin account: A single shared username/password for pulls/pushes — simple but not recommended for production (prefer Entra ID/managed identity or repository-scoped tokens).
  • Tasks (ACR Tasks): Build images in Azure on git push or base-image updates without a local Docker engine.
  • Geo-replication (Premium only) keeps a single registry available and low-latency across multiple regions.

Azure Container Instances (ACI)

ACI is a serverless container platform for running Docker containers on demand without infrastructure management. It supports container groups that share lifecycle, resources, local network, and storage volumes.

Azure Container Apps

A fully managed service, built on Kubernetes and Dapr under the hood, for deploying, managing, and scaling multi-container applications and microservices without managing cloud infrastructure or complex container orchestration.

Sizing & Scaling Comparison

Aspect ACI Container Apps
Sizing model Specify vCPU and memory per container group at creation (billed per second for the resources reserved). Specify CPU/memory per container revision; resources shared across replicas within an app.
Scaling No built-in autoscaling — one container group is a fixed unit; scale by orchestrating multiple groups externally. Built-in autoscale (KEDA-based) on HTTP traffic, CPU/memory, or custom/event-driven metrics (e.g. queue length).
Scale to zero Not supported — group runs until explicitly stopped/deleted. Supported — can scale replicas down to 0 when idle, and back up on demand.
Best fit Simple, short-lived, or burst workloads (batch jobs, CI/CD agents). Long-running microservices, APIs, and event-driven apps needing revisions and traffic splitting.
