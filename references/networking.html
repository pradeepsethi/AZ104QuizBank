Networking Domain Scope

Domain Overview: Virtual networking in AZ-104 covers virtual networks, secure access, name resolution, network routing, and load balancing services.

Virtual Network Essentials

  • VNets & Subnets: Dual-stack IPv4/IPv6 addressing with custom CIDR ranges divided into subnets.
  • NAT Gateway: Provides outbound internet connectivity for subnets without requiring public IPs on VMs.
  • Service Endpoints: Secures Azure service resources to virtual network address spaces over the Azure backbone.

Public IP Addresses

Public IPs enable inbound/outbound internet connectivity for resources such as VMs, load balancers, Application Gateway, and Bastion.

SKU Comparison

Attribute Basic SKU Standard SKU
Allocation Static or Dynamic Static only
Security Open by default (no NSG required) Secure by default — traffic denied unless allowed by NSG
Availability Zones Not zone-redundant Supports zonal & zone-redundant deployment
Pairing Rule Can pair with Basic Load Balancer Must pair with Standard Load Balancer
Exam Tip: SKUs cannot be mixed — a Standard SKU public IP can only be associated with Standard SKU resources (Load Balancer, VM NIC, etc.). Basic SKU public IPs are being retired, so Standard is the default choice going forward.

Allocation Methods

  • Dynamic: Assigned when the resource is started, can change on stop/deallocate (Basic SKU only).
  • Static: Assigned immediately and remains fixed for the resource's lifetime.

Network Routing

Azure automatically creates system routes for VNet, subnet, and on-premises traffic. User-defined routes (UDRs) override this default behavior via route tables.

Route Tables & Next Hop Types

Next Hop Type Description
Virtual Network Gateway Routes traffic through a VPN/ExpressRoute gateway.
Virtual Network Routes traffic within the VNet address space.
Internet Routes traffic to the public internet.
Virtual Appliance Routes traffic to a specific IP, typically an NVA (e.g. firewall).
None Drops traffic matching the route (blackhole route).
Route Precedence: User-defined routes take priority over BGP routes, which take priority over Azure's default system routes. The most specific prefix always wins regardless of route source.

Network Security Groups & Application Security Groups

NSGs and ASGs control and categorize network traffic boundaries within your virtual network.

NSG vs ASG Comparison

Feature Network Security Group (NSG) Application Security Group (ASG)
Primary Function Enforces and controls network traffic rules. Logical grouping object referenced in NSG rules.
Scope Attached at Subnet or NIC level. Grouped at Network Interface (NIC) level.
Limits Supports up to 1,000 security rules. Up to 100 ASGs specified per NSG rule set.
Rule Action Supports Allow and Deny. Supports Allow and Deny.

Evaluate Effective Security Rules

A NIC can be affected by NSGs applied at both the subnet and NIC level, so Azure evaluates the combined ("effective") rule set to determine actual traffic behavior.

  • Rule Processing Order: Rules are processed by priority number (lowest first, 100–4096); the first match wins and processing stops.
  • Combining NSGs: When both subnet and NIC NSGs apply, traffic must be allowed by both for inbound, and either can independently allow outbound.
  • Effective Security Rules view: Found in a NIC's Network Watcher blade — shows the full merged list of rules (including default rules) actually being applied, useful for diagnosing unexpected allow/deny behavior.
  • Default Rules: Every NSG includes non-removable defaults — Allow VNet inbound/outbound, Allow Azure Load Balancer inbound, and Deny all inbound/outbound (lowest priority, 65000+).

Connectivity & Secure Access

Virtual Network Peering

  • VNet Peering: Links VNets within the same region with high-bandwidth, low-latency connectivity.
  • Global VNet Peering: Connects VNets across different Azure regions.
  • Key Properties: Private traffic flow, no gateways required, and no downtime during creation. Non-overlapping address spaces required.

Azure Bastion

Fully managed PaaS providing seamless and secure RDP/SSH access directly through a browser using TLS/SSL without exposing public IP addresses on target VMs.

Service Endpoints vs Private Endpoints

Both secure connectivity to Azure PaaS resources (e.g. Storage, SQL Database) over the Microsoft backbone instead of the public internet, but they work differently.

Feature Service Endpoint Private Endpoint
IP Address PaaS resource keeps its public IP; traffic stays on Azure backbone PaaS resource gets a private IP inside your VNet
Direction Extends VNet identity to the service (outbound only) Projects the service into your VNet (inbound)
On-Premises Access Not accessible from on-premises networks Accessible via VPN/ExpressRoute from on-premises
Data Exfiltration Protection Limited — other resources in same service may still be reachable Strong — maps to a single specific resource instance
DNS No DNS changes needed Requires Private DNS Zone integration to resolve correctly
Cost Free Billed per hour + data processed
Exam Tip: Choose Private Endpoints when you need on-premises access, strict data exfiltration protection, or a single dedicated private IP. Service Endpoints are simpler and free but only secure traffic originating from within Azure.

Azure DNS

Azure DNS hosts DNS domains and provides name resolution using Microsoft's global network of name servers.

Zone Types

  • Public DNS Zone: Resolves domain names accessible from the internet (e.g. contoso.com).
  • Private DNS Zone: Resolves names within one or more linked VNets; not resolvable from the internet. Supports auto-registration of VM records.

Common Record Types

Record Type Purpose
A Maps a hostname to an IPv4 address.
AAAA Maps a hostname to an IPv6 address.
CNAME Maps an alias hostname to another hostname.
MX Directs mail to mail servers.
TXT Holds arbitrary text, often used for domain verification (e.g. SPF).
NS / SOA Name server delegation and zone authority information (auto-created with the zone).
Virtual Network Links: A Private DNS Zone must be explicitly linked to each VNet that should use it for resolution; enable "Auto registration" so VM DNS records are added/removed automatically as VMs are created/deleted.

Public vs Internal Load Balancer

  • Public Load Balancer: Frontend has a public IP; load balances internet-facing traffic to backend pool VMs, and can also provide outbound SNAT.
  • Internal (Private) Load Balancer: Frontend uses a private IP from the VNet; load balances traffic between resources inside a VNet, or from on-premises via VPN/ExpressRoute.

Health Probes

Health probes determine which backend instances are healthy and eligible to receive new traffic. Supported protocols: TCP, HTTP, and HTTPS. An instance that fails the probe threshold is taken out of rotation until it passes again.

Network Watcher & Troubleshooting

Network Watcher provides a suite of tools to monitor, diagnose, and troubleshoot connectivity and load balancing issues in Azure VNets.

Tool Purpose
IP Flow Verify Checks whether a specific packet (source/dest IP, port, protocol) is allowed or denied by NSG rules to/from a VM.
Connection Troubleshoot Tests connectivity between a VM and an endpoint (VM, FQDN, URI, IP), reporting latency and the hop where failure occurs.
Next Hop Shows the next hop type and route a packet will take from a VM toward a destination IP — useful for verifying UDRs.
Effective Routes Displays the combined set of system routes and UDRs actually applied to a NIC.
Effective Security Rules Displays the combined set of subnet and NIC-level NSG rules actually applied to a NIC.
NSG Flow Logs Logs allowed/denied traffic through an NSG for auditing and traffic analytics (via Traffic Analytics).
Packet Capture Captures packet-level traffic to/from a VM for deep inspection, triggerable by alerts.

Troubleshooting Load Balancers

  • Health probe status: Check backend health via the "Insights" / "Health probe status" blade — a probe failure removes an instance from rotation.
  • NSG rules: Ensure NSGs allow traffic from the AzureLoadBalancer service tag on probe ports and from the client source on the load-balancing rule port.
  • Backend pool config: Confirm VMs/VMSS are correctly associated with the backend pool and the load-balancing rule's frontend/backend port mapping.
  • OS-level firewall: The guest OS firewall (e.g. Windows Firewall) can silently block probe or data traffic even when NSGs allow it.
