Monitoring & Backup Domain Scope

Domain Overview: Monitor and backup Azure resources in AZ-104 covers Azure Monitor metrics and logs, alerting, monitoring insights, Network Watcher, and implementing backup and recovery with Azure Backup and Site Recovery.

Monitor Resources in Azure

  • Metrics & Logs: Numeric time-series metrics and queryable log data collected by Azure Monitor.
  • Alerting: Alert rules, action groups, and alert processing rules that notify or automate responses to conditions.
  • Insights: Curated dashboards for VMs, storage accounts, and networks built on top of Azure Monitor data.

Metrics in Azure Monitor

Azure Monitor Metrics is a lightweight, time-series database that stores numeric values describing an aspect of a resource at a particular point in time. Metrics are collected automatically for most Azure resources.

Metric Types

Type Description
Platform metrics Created automatically by Azure resources (e.g. CPU %, disk IOPS, network in/out). Collected at 1-minute frequency by default and typically retained for 93 days.
Custom metrics Defined by an application or the Azure Monitor agent/guest OS. Sent via the Application Insights SDK or Azure Monitor Agent.
Guest OS metrics Collected from inside a VM (memory, disk space, process info) via a diagnostics extension or the Azure Monitor Agent, unlike host-level platform metrics.

Metrics Explorer

Used to plot charts, visually correlate trends, and investigate spikes/dips in metric values. Supports splitting by dimension (e.g. per-disk or per-instance) and aggregation types: Sum, Avg, Min, Max, Count. Charts can be pinned to a dashboard or exported to a workbook.

Metrics vs Logs

Aspect Metrics Logs
Data type Numeric, time-series Text/structured records (tables)
Storage Metrics database Log Analytics workspace
Query language Metrics Explorer (no query language needed) KQL
Latency Near real-time Slightly higher ingestion latency
Best for Near real-time alerting, lightweight dashboards Deep analysis, correlation across data types
Exam Tip: If a question asks for the fastest/lightest way to alert on a threshold (e.g. CPU > 80%), the metric-based alert is usually the better answer than a log query alert, since metric alerts evaluate faster.

Monitor Agent & Log Queries

All log data obtained by Azure Monitor is stored in a Log Analytics workspace and retrieved using a log query written in Kusto Query Language (KQL).

Query Building Blocks

  • Table-based queries — the query organizes log data into tables.
  • Search queries — use this query if you need to find a specific value in your table.
  • Sort and top — sort the preferred column to display results in a particular order; use top to get the latest records in the entire table.
  • Where — adds a filter to a query; different expressions can be used for filter conditions.
  • Time filter — defines a specific time range by adding the time filter to the query.
  • Project and Extend — project selects specific columns, while extend adds additional columns.
  • Summarize — identifies a group of records and applies aggregations using the summarize operator.

Monitor Agent Limits

Limits and Capabilities:
  • If a query includes workspaces in 20 or more regions, the query will be blocked from running.
  • Monitor Agent results are limited to a maximum of 10,000 records.
  • A monitor agent can collect logs and performance data from virtual or physical devices outside Azure.
  • A monitor agent cannot send data to Azure Monitor Metrics, Azure Storage, or Azure Event Hubs.

Log Settings & Diagnostics

Diagnostic settings are how a resource's platform logs and metrics get routed into Azure Monitor (and other destinations) for analysis and retention.

Diagnostic Settings Destinations

  • Log Analytics workspace: for querying with KQL, alerting, and dashboards.
  • Azure Storage account: for cheap long-term archival/audit retention.
  • Azure Event Hubs: to stream logs to a third-party SIEM or a custom pipeline.
  • Partner solution: send data directly to a supported partner monitoring solution.

Log Categories

  • Administrative: record of create/update/delete (control-plane) operations.
  • Activity log: subscription-level events (who did what, when); retained 90 days by default and can be routed via diagnostic settings for longer retention.
  • Resource logs: operations performed within a resource (data-plane), category set differs per resource type.
Key Point: Diagnostic settings must be configured per resource (or applied at scale via Azure Policy). Without a diagnostic setting, resource logs are not retained anywhere for later query.

Alert Rules, Action Groups & Processing Rules

Alert Rule Anatomy

An alert rule has three parts: a target resource (or scope), a condition (a signal/metric or log query plus a threshold), and one or more action groups to notify or trigger automation when the condition is met. Alert rule types include Metric alerts (near real-time, evaluate metric data), Log alerts (run a scheduled KQL query), Activity log alerts (fire when a specific control-plane event occurs, e.g. resource deleted), and Smart detection alerts (Application Insights anomaly detection).

Alert Processing Rules

Alert processing rules (formerly "action rules") help define or suppress actions at any Azure Resource Manager scope: Azure subscription, resource group, or target resource. They provide filters that narrow down the specific subset of alert instances on which to act.

  • Used to add or suppress action groups across many alert rules at once — e.g. suppress all notifications for a resource group during planned maintenance.
  • Can be scheduled (one-time or recurring window) so notifications automatically resume afterward.
  • Applied on top of alert rules; they don't replace the alert rule's own action group configuration, they modify what actually fires.

Action Groups

An action group is a collection of notification preferences defined by the owner of an Azure subscription. Azure Monitor and Service Health alerts use action groups to notify users when an alert is triggered. Different alerts can use the same action group or different action groups depending on requirements.

Worked Example

Signal Signal Type Users Notified
Availability Metric User 1, User 2, User 3
Transactions Metric User 2, User 3
Create/Update Storage Account Activity Log User 1, User 2, User 3
Regenerate Storage Account Keys Activity Log User 3
Answer: Create 4 alert rules — one per signal type. Create 3 action groups — one for each unique set of users to be notified.

Azure Log Analytics

Azure Log Analytics is primarily designed for collecting, analyzing, and visualizing log and performance data from diverse resources within an Azure environment. As part of Azure Monitor, it enables users to run queries on logs and metrics to gain insights into system performance, security posture, and overall health.

Mode Description
Simple Mode Designed for users unfamiliar with complex query languages. Provides a clear interface for creating basic queries using prebuilt templates and filters, suitable for quick exploration and troubleshooting without writing code.
KQL Mode Kusto Query Language (KQL) is used for advanced data exploration — purpose-built for big-data analytics and suitable for complex searches, aggregations, visualizations, custom reports, and extracting specific insights from extensive log data.

Azure Monitor Insights

Insights are curated, pre-built monitoring experiences layered on top of Azure Monitor. They save you from building metrics/log queries and dashboards from scratch.

VM Insights

Monitors the health and performance of Azure VMs, scale sets, and hybrid/on-premises VMs. Requires the Azure Monitor Agent plus the Dependency Agent (for the map feature). Provides three views: Overview (health/state at a glance), Performance (CPU, memory, disk, network trends with adjustable percentiles), and Map (process-level dependencies and connections between VMs). Data is stored in a Log Analytics workspace, so it can also be queried directly with KQL.

Storage Insights

Surfaces capacity, availability, performance, and failure metrics for storage accounts (Blob, File, Queue, Table). Provides a top-level view across all storage accounts in a subscription, plus a drill-down view per account showing transaction breakdowns by API, response type, and geo-replication status. Built on platform metrics — no agent installation required.

Network Insights

Provides a topology-centric view of network resources (VNets, NICs, load balancers, gateways, ExpressRoute circuits) and their health. Aggregates data already collected by Network Watcher, Connection Monitor, and platform metrics into one dashboard rather than being a separate data-collection mechanism.

Exam Tip: "Insights" are dashboards/experiences, not separate data stores — the underlying data still comes from Azure Monitor Metrics, Log Analytics, or Network Watcher.

Network Watcher & Connection Monitor

Network Connectivity Monitoring

The designated tool to monitor communication between a VM and an endpoint is Connection Monitor. An endpoint can be an IPv4 address, URI, FQDN, or virtual machine. Connection Monitor displays the minimum, average, and maximum latency detected over time; latency can be reduced by relocating Azure resources to different Azure regions.

Diagnosing Virtual Machine Network Traffic

IP flow verify is used to diagnose network traffic problems to or from a VM. It specifies the source and destination IPv4 address, protocol, port, and traffic direction. The result indicates whether the connection succeeds or fails and, if it fails, which security rule allowed or denied the communication.

Verify a TCP Connection From a VM

Connection troubleshoot diagnoses outbound connections from a virtual machine. It can test a VM connection to an IPv4 address, URI, FQDN, or another VM, providing a point-in-time result and identifying possible causes when an endpoint is unreachable, including:

  • DNS resolution failures
  • High VM CPU and memory utilization
  • NSG and firewall rules that block traffic
  • Misconfigured or missing routes

Analyze Ingress and Egress IP Traffic Through an NSG

Network Security Groups (NSGs) allow or deny inbound and outbound traffic to a network interface. NSG flow logs can help optimize network flows, detect intrusions, monitor throughput, and verify compliance.

Backup Azure Virtual Machines

To prevent unintended destruction or deletion of data on a virtual machine, the guide recommends creating a backup. Azure Backup can back up on-premises machines, workloads, and Azure VMs.

Backup Schedule and Retention

Backup schedule can be daily or weekly. Retention can be configured on a daily, weekly, monthly, and yearly schedule.

VM State: A stopped/deallocated VM only stops the virtual machine; Azure Backup takes snapshots of the VM disks. A backup can still be created whether the VM is running or stopped, as long as the disk is attached to the VM.

Recovery Services Vault

A Recovery Services vault is a storage entity that stores data and recovery points created over time — a copy of data or configuration information for virtual machines, workloads, or servers. Backup data sources or VMs must be in the same region as the Recovery Services vault, though they can have different resource groups or operating systems.

Backup and Restore Operations

Triggering a Backup

An initial (first) backup can be triggered on demand right after configuring a backup policy, rather than waiting for the next scheduled run. On-demand backups can optionally use a retention period different from the policy's scheduled retention.

VM Restore Options

Option Description
Create a new VM Fastest option — Azure Backup creates a brand-new VM from the recovery point, in the same or a different resource group/VNet.
Restore disk(s) Restores only the disks (as VHDs in storage or as managed disks); you then attach them to a new or existing VM manually, or generate an ARM template.
Replace existing disks Overwrites the disks currently attached to the original VM with the versions from the recovery point — used to roll an existing VM back in place.
Cross-region restore Restores a VM/disk into Azure Backup's secondary (paired) region, for testing DR readiness or recovering from a regional outage — requires cross-region restore to be enabled on the vault.

File-Level and Item-Level Recovery

File Recovery lets you browse and copy individual files/folders from a recovery point without restoring the whole VM, using a downloadable script that mounts the recovery point as a local drive. Workload-aware backups (SQL/SAP HANA in a VM) support restoring an individual database rather than the whole VM.

Soft Delete: Deleted backup data is retained in a soft-deleted state (default 14 days) so it can still be recovered/undeleted if a vault or backup item is removed accidentally or maliciously.

Backup Components & Vault Considerations

Recovery Services Vault Dependencies

A Recovery Services vault cannot be deleted if it contains protected data sources (IaaS VMs, SQL databases, Azure file shares), backup data, backup data in a soft-deleted state, or registered storage accounts. If deletion fails with "Failed to delete resource group", stop the backup first, then disable soft delete and delete the resource group.

Microsoft Azure Recovery Services (MARS) Agent

The MARS agent allows backup of data from Windows virtual machines and on-premises machines, with backups stored directly in the Recovery Services vault. Installing the MARS agent and performing backups requires a Recovery Services vault, a backup policy, and a secure route (ExpressRoute or Private Endpoint).

Azure Backup Vault

Azure Backup Vault is a storage entity for backup data for various Azure services, designed to support newer workloads and services such as Azure Database for PostgreSQL servers.

  • Simplifies organization of backup data and reduces management overhead.
  • Includes enhanced security features to protect cloud backups and support safe data recovery.
  • Supports Azure RBAC for fine-grained access management.
  • Provides data isolation by storing backup data in a Microsoft-managed Azure subscription and tenant separate from the production environment.
  • Handles storage and encryption settings, including platform-managed keys and customer-managed keys for backup data encryption.

Backup Policy

To create a Backup Policy:

  1. Select a datasource type: Azure Virtual Machines or Azure Database for PostgreSQL servers.
  2. Choose the frequency: daily or weekly.
  3. Enter how many days to retain recovery snapshots.
  4. Instant recovery snapshots can be retained for at most 5 days.
  5. Choose the backup retention range: daily, weekly, monthly, or yearly.

Azure Site Recovery & Disaster Recovery

For hybrid backup solutions, site-to-site recovery, or a business continuity and disaster recovery (BCDR) strategy, Azure Site Recovery replicates workloads from a primary site to a secondary site. If the primary site suffers an outage and becomes unavailable, Azure Site Recovery can automatically fail over to the secondary site so services continue working.

Resources That Can Be Replicated

  • Azure Virtual Machines (cross-region replication)
  • Any operating system
  • On-premises to Azure
  • Other cloud service providers to Azure
  • VMware, Hyper-V, or physical servers

RTO and RPO

Term Definition
RTO — Recovery Time Objective The time it takes after a disruption to restore a business process to its service level.
RPO — Recovery Point Objective The acceptable amount of data loss measured in time before the disaster occurs.

Failover to a Secondary Region

Failover Types

Type Description
Test failover Validates the DR plan without impacting production or ongoing replication — spins up an isolated copy VM in the target region/VNet for verification, then is cleaned up.
Planned failover Used for expected downtime (e.g. scheduled maintenance). Ensures zero data loss by synchronizing any final changes from the source before failing over.
Unplanned failover Used after an unexpected outage. Attempts to replicate any final changes if the source is still reachable, but proceeds even if it isn't — may involve some data loss depending on the last successful recovery point.

Failover Workflow

  1. Initiate failover and choose a recovery point (latest, latest processed, or a specific app-consistent point).
  2. Azure Site Recovery brings up the VM(s) in the secondary/target region.
  3. Commit the failover once you've confirmed the failed-over VMs are healthy — this deletes other recovery points and finalizes the switch.

Failback

After the primary region/site is available again, reprotect the VMs (reverse replication direction back to the original region) and then fail over again to move workloads back — restoring the original replication direction.

Backup Reports & Alerts

Backup Reports

Cross-vault, cross-subscription reporting built on Azure Monitor/Log Analytics, showing backup jobs, alerts, usage/cloud storage consumption, and policy compliance over time. Requires a diagnostic setting on each Recovery Services vault that routes backup data to a Log Analytics workspace (or storage account) used by the report — useful for answering questions like "which VMs failed their last backup" across the whole environment, not just one vault.

Backup Alerts

Built-in alerts fire automatically for events such as backup failures, a VM stopped being protected (deletion/expired retention), or excessive storage consumption — no separate alert rule needs to be authored for these. Configured per Recovery Services vault under Backup Alerts & Notifications, and can be routed through action groups (email, SMS, webhook, Logic App) the same way Azure Monitor alerts are.

Security Alerts: Alerts for events like disabling soft delete or multiple backup deletions in a short window are enabled by default to help detect malicious or accidental deletion attempts.
