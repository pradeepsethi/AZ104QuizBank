Microsoft Entra ID (formerly Azure Active Directory)

Microsoft Entra ID is Microsoft’s cloud-based identity and access management service. It helps employees sign in and access resources across external services (like Office 365, Azure Portal, and SaaS applications) as well as internal network applications.

Initial Domain Name: Every new Microsoft Entra ID tenant comes with an initial domain name in the format <domainname>.onmicrosoft.com. While this cannot be changed or deleted, you can register custom domain names (e.g., azure@az104exam.com).

Key Features & Concepts

  • Managing Users, Groups, Roles, and Devices: Administer user accounts, security/Microsoft 365 groups, directory roles, and device join states[cite: 3].
  • Custom Domain Verification: Custom domains added to Microsoft Entra ID can be verified using either TXT or MX DNS record types.
  • Authentication & Protection: Automatic integration with Microsoft Online business services to protect identity and access.

Creating & Managing Users

  • Creation Methods: New users can be created individually in the Entra admin center/Azure Portal, in bulk via CSV upload, or scripted with Azure PowerShell (New-AzADUser) / Azure CLI (az ad user create). Users can also be synced in from an on-premises Active Directory using Microsoft Entra Connect.
  • User Types:
    • Member — A native, internal user of the tenant (default type).
    • Guest — An external identity invited into the tenant via B2B collaboration.
  • User Properties: Profile info (name, job title, department), contact info, and extension attributes/custom attributes can be edited per-user or in bulk. The Block Sign-In setting disables a user's account without deleting it. Deleted users land in a recoverable state for 30 days before permanent removal.

User & Group Management Essentials

  • Group Types:
    • Security Groups — Used to manage access to resources and policies for groups of users/devices.
    • Microsoft 365 Groups — Provides collaboration opportunities by giving members access to shared mailboxes, calendars, files, and SharePoint sites.
  • Membership Types:
    • Assigned — Static allocation where users are added/removed manually.
    • Dynamic User / Dynamic Device — Automatically populates membership based on dynamic user attributes (e.g., user.department -eq "IT"). Requires Microsoft Entra ID P1 license.
  • Administrative Units (AUs): Containers used to delegate administrative control over subsets of users, groups, or devices without granting tenant-wide administrator access.
  • Group-Based Licensing: Assigns Microsoft Entra P1/P2 or Microsoft 365 licenses automatically to all members of a group, simplifying license lifecycles.

License Management

  • Assignment Methods: Licenses can be assigned directly to individual users or automatically via group-based licensing. Group-based assignment is preferred at scale since it re-evaluates automatically as group membership changes.
  • License Conflicts: If a group-assigned license can't be applied (e.g., conflicting service plans, missing usage location), Entra ID flags the user with a licensing problem while continuing to apply the rest of the group's licenses.
  • Usage Location: A user's Usage Location attribute must be set before a license can be assigned, since license availability varies by country/region.

External Identities & Collaboration

  • B2B Collaboration: Allows external guest users to log in with their own corporate or personal credentials while retaining access controls over your tenant's resources.
  • Inviting Guests: Guests can be invited individually (email invite, requiring redemption) or in bulk via CSV. Guest access is governed by External collaboration settings, which control who can invite guests and what guests can see in the directory.
  • Self-Service Password Reset (SSPR): Allows users to reset their passwords without administrator intervention. Configurable with authentication methods (SMS, Mobile App Notification, Email) and optional password writeback to on-premises Active Directory.

Azure Role-Based Access Control (RBAC)

Azure RBAC helps you manage who has access to Azure resources, what they can do with those resources, and what areas they have access to[cite: 3].

How Permissions Are Enforced

Permissions are assigned by creating role assignments. A role assignment consists of three elements: a principal (user, group, service principal, or managed identity), a role definition, and a scope.

Different Types of Roles

  • Owner: Full access to all resources, including the authority to assign roles to others.
  • Contributor: Can create and manage all types of Azure resources, but cannot grant access to others.
  • Reader: Can view existing Azure resources.
  • User Access Administrator: Allows managing user access to Azure resources.
  • Virtual Machine Contributor: Can manage VMs but not the virtual network or storage account they connect to.
  • Storage Account Contributor: Can manage storage accounts but not access to them via RBAC.
  • Network Contributor: Can manage networking resources (VNets, NSGs, public IPs, etc.).
  • Security Admin: Manage security-related policies, view alerts and recommendations in Microsoft Defender for Cloud.
  • Backup Contributor: Manage backup services, except removal/deletion of the Recovery Services vault.
  • Custom Roles: Custom-tailored roles if built-in roles do not meet specific organizational requirements.

Role Definition Structure

A role definition is a collection of permissions defined in a JSON file format that includes operations for Actions, NotActions, DataActions, NotDataActions, and AssignableScopes.

Assigning Roles at Different Scopes

Role assignments can be applied at four levels, from broadest to narrowest, and are inherited downward to all child scopes:

Management Group → Subscription → Resource Group → Resource

Best practice is to assign roles at the narrowest scope needed to perform the job (principle of least privilege), rather than defaulting to broader scopes for convenience.

Interpreting Access Assignments

  • Cumulative/Additive Access: Azure RBAC is additive — a principal's effective permissions are the union of all role assignments across every scope that applies to it (direct assignment + inherited + group membership). There is no explicit "deny" assignment in classic RBAC (deny assignments exist only for specific system scenarios, e.g. Azure Blueprints/managed apps).
  • Check Access: Use the Check access button on a resource's Access Control (IAM) blade to see what a specific user, group, or service principal can do at that scope.
  • View My Access / Role Assignments: The Role assignments tab lists every principal with a role at that scope and above (inherited), noting the scope each assignment condition originates from.
  • RBAC vs. Policy Conflicts: RBAC controls who can do what; Azure Policy controls what configurations are allowed, regardless of who the user is. A user might have RBAC "Contributor" access yet still be blocked by a Policy with a Deny effect.

Managed Identities for Azure Resources

Eliminates the need for developers to manage credentials in code by providing an automatically managed identity in Microsoft Entra ID for applications:

  • System-Assigned: Tied directly to a single Azure resource (e.g., a VM). Deleted automatically when the resource is deleted.
  • User-Assigned: Created as a standalone Azure resource. Can be assigned to multiple Azure resources simultaneously.

Azure Policy & Resource Governance

Azure Policy enforces organizational standards and assesses compliance at scale through its governance capabilities.

Policy Components & Structure

  • Policy Definition: Expressed in JSON, defining the conditions under which a policy is enforced and the action to take.
  • Policy Assignment: A policy definition or initiative that has been assigned to a specific scope (e.g., Management Group, Subscription, or Resource Group).
  • Initiative Definition: A collection of policy definitions grouped together toward a single overarching goal.

Policy Effects

Policy evaluation triggers specific effects depending on rules specified in the definition:

  • Append — Adds required fields to the resource during creation or update.
  • Audit — Creates a warning event in the activity log without blocking the request.
  • AuditIfNotExists — Audits if a related resource does not exist.
  • Deny — Prevents the resource creation or update request.
  • DeployIfNotExists — Deploys a specified resource if it does not already exist.
  • Disabled — Turns off policy evaluation.

Management Groups & Resource Locks

  • Management Groups: Governance scope hierarchy above subscriptions, supporting up to 6 levels deep (not counting the root or subscription level). Every tenant has a single top-level Root management group. Policy assignments and RBAC roles assigned at a Management Group automatically inherit down to child subscriptions and resources. A subscription can only be a member of one management group at a time; management groups can be nested and subscriptions moved between them.
  • Resource Locks: Protects Azure resources from accidental modification or deletion.
    • CanNotDelete (Delete) — Authorized users can read and modify a resource, but cannot delete it.
    • ReadOnly (Read-only) — Authorized users can read a resource, but cannot modify or delete it (this can break operations that require a write, such as scaling).
    Locks apply to all users/roles, including Owners, and are inherited from parent scope. A resource inherits the most restrictive lock from any parent scope. Deleting a resource group with a lock is blocked even if individual resources are unlocked.

Resource Tags

Tags are name/value pairs applied to resources, resource groups, and subscriptions to logically organize assets for billing, automation, and management purposes.

Key Rules & Constraints

  • Each resource, resource group, or subscription can have up to 50 tag name/value pairs. Storage accounts and some resources support fewer.
  • Tag name/value pairs are not inherited automatically by child resources — applying a tag to a resource group does not tag the resources inside it. Use Azure Policy (Modify effect) to enforce/inherit tags automatically.
  • Tags can be applied/edited via the Portal, Azure PowerShell, Azure CLI, or ARM/Bicep templates, and can be bulk-edited across multiple resources at once.
  • Certain resource types don't support tags (e.g., some classic resources); check resource-specific documentation.
  • Tags are useful for cost reporting — Cost Management can group and filter spend by tag.

Resource Groups

A resource group is a logical container that holds related resources for an Azure solution, used for lifecycle management, access control, and billing/reporting grouping.

Key Facts

  • Every resource must belong to exactly one resource group. Resources can be moved between resource groups (and even subscriptions), though some resource types have move limitations.
  • Resource groups cannot be nested.
  • The resource group stores metadata about resources in a specific region; if that region has an outage, the metadata may be unavailable even though the resources themselves reside in other regions and keep running.
  • Deleting a resource group deletes all resources within it — apply a CanNotDelete lock to prevent accidental loss.
  • RBAC roles and Azure Policy can be assigned at the resource group scope and are inherited by all resources inside.

Azure Subscriptions

A subscription is a billing and access-control boundary that links to an Entra ID tenant and groups resource groups/resources together.

Key Concepts

  • Subscription Types: Common offer types include Pay-As-You-Go, Enterprise Agreement (EA), Cloud Solution Provider (CSP), Free Trial, and Microsoft Customer Agreement (MCA) — each with different billing and support arrangements.
  • Tenant Relationship: A subscription trusts exactly one Entra ID tenant for authentication, but a tenant can be associated with multiple subscriptions. Subscription ownership (the associated Entra tenant) can be changed via the "Change directory" action, though this can affect existing role assignments.
  • Multiple Subscriptions: Organizations often create multiple subscriptions to separate environments (Dev/Test/Prod), billing units, or compliance boundaries — grouped under Management Groups for unified governance.
  • Moving Subscriptions: Subscriptions can be moved between Management Groups; moving between tenants is a more involved process and can break existing RBAC assignments and managed identities.
  • Cancel/Reactivate: Subscriptions can be cancelled (resources are deallocated/deleted after a grace period) or, in some cases, reactivated within a limited window.

Cost Management: Alerts, Budgets & Advisor

Budgets & Alerts

  • Budgets: Set in Cost Management + Billing at the subscription, resource group, or management group scope to track spend against a defined amount over a time period (monthly, quarterly, annually).
  • Cost Alerts: Automatically triggered notifications when actual or forecasted spend crosses a defined percentage threshold of the budget (e.g., 80%, 100%). Alerts are notification-only — they do not stop resources or block spending.
  • Action Groups: Budgets can trigger action groups to automate a response (e.g., send an email, call a webhook/Azure Function/Logic App) when a threshold is exceeded.
  • Cost Analysis: A tool for exploring and visualizing accumulated/actual costs over time, filterable and groupable by resource, resource group, tag, or service.

Azure Advisor

Azure Advisor is a free, personalized recommendation engine that analyzes resource configuration and usage telemetry across five categories:

  • Cost: Identifies underutilized resources (e.g., right-sizing or shutting down idle VMs) and reserved instance opportunities to reduce spend.
  • Reliability: Recommendations to ensure business continuity and availability.
  • Security: Surfaces Microsoft Defender for Cloud recommendations.
  • Operational Excellence: Process and workflow best practices.
  • Performance: Improves the speed/responsiveness of applications.
