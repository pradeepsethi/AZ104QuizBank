Networking Domain Scope

Domain Overview: Implement and manage virtual networking in AZ-104 covers creating and configuring virtual networks and subnets, public IP addresses, user-defined routes, network security groups and application security groups, Azure Bastion, service and private endpoints, Azure DNS, load balancing, and network troubleshooting with Azure Network Watcher and Connection Monitor.

Virtual Network Essentials

  • VNets: Provide private networking boundaries in Azure. A VNet can contain one or more IPv4 and/or IPv6 address spaces.
  • Address Spaces & Subnets: VNet address spaces use CIDR notation and are divided into non-overlapping subnets. Subnet ranges must be contained within the VNet address space and cannot overlap each other.
  • Subnet Delegation: Allows a subnet to be dedicated to a specific Azure service that requires delegated permissions, such as Azure Kubernetes Service.
  • NAT Gateway: Provides predictable outbound internet connectivity for resources in an associated subnet without requiring a public IP on each VM. NAT Gateway does not provide unsolicited inbound connectivity.
  • Service Endpoints: Extend a VNet's identity to supported Azure services so access can be restricted to selected VNets/subnets while traffic remains on the Azure backbone.

Public IP Addresses

Public IPs provide internet-facing connectivity for supported Azure resources such as VMs, load balancers, Application Gateway, and Bastion.

Allocation Methods

  • Static: The public IP address is assigned when the resource is created and remains associated until the resource association or public IP resource is changed.
  • Dynamic: Legacy Basic SKU allocation behavior; do not treat it as a current Standard public IP option.

Network Routing

Azure automatically creates system routes for VNet, subnet, and on-premises traffic. User-defined routes (UDRs) override this default behavior via route tables.

Route Tables & Next Hop Types

Next Hop Type Description
Virtual Network Gateway Routes traffic through a VPN/ExpressRoute gateway.
Virtual Network Routes traffic within the VNet address space.
Internet Routes traffic to the public internet.
Virtual Appliance Routes traffic to a specific IP, typically an NVA (e.g. firewall).
None Drops traffic matching the route (blackhole route).
Route Precedence: User-defined routes take priority over BGP routes, which take priority over Azure's default system routes. The most specific prefix always wins regardless of route source.

Network Security Groups & Application Security Groups

NSGs and ASGs control and categorize network traffic boundaries within your virtual network.

NSG vs ASG Comparison

Feature Network Security Group (NSG) Application Security Group (ASG)
Primary Function Enforces and controls network traffic rules. Logical grouping object referenced in NSG rules.
Scope Attached at Subnet or NIC level. Grouped at Network Interface (NIC) level.
Limits Supports up to 2,000 security rules, including default rules. Up to 10 ASGs can be referenced as the source or destination in a single NSG rule.
Rule Action Supports Allow and Deny. ASG is a grouping construct referenced by NSG rules; it does not have its own Allow/Deny action.

Evaluate Effective Security Rules

A NIC can be affected by NSGs applied at both the subnet and NIC level, so Azure evaluates the combined ("effective") rule set to determine actual traffic behavior.

  • Rule Processing Order: Rules are processed by priority number (lowest first, 100–4096); the first match wins and processing stops.
  • Combining NSGs: When both subnet and NIC NSGs apply, both NSGs must allow the traffic. For inbound traffic, the subnet NSG is evaluated before the NIC NSG. For outbound traffic, the NIC NSG is evaluated before the subnet NSG. A deny at either level blocks the traffic.
  • Effective Security Rules view: Found in a NIC's Network Watcher blade — shows the full merged list of rules (including default rules) actually being applied, useful for diagnosing unexpected allow/deny behavior.
  • Default Rules: Every NSG includes non-removable defaults — Allow VNet inbound/outbound, Allow Azure Load Balancer inbound, and Deny all inbound/outbound (lowest priority, 65000+).

Connectivity & Secure Access

Virtual Network Peering

  • VNet Peering: Connects VNets in the same Azure region with private, high-bandwidth, low-latency connectivity over the Microsoft backbone.
  • Global VNet Peering: Connects VNets across different Azure regions.
  • Address Spaces: Peered VNets must use non-overlapping address spaces.
  • Non-transitive: VNet peering is not transitive; if Spoke A is peered with Hub and Spoke B is peered with Hub, Spoke A cannot communicate with Spoke B through the Hub unless you explicitly design forwarding/routing through the Hub.
  • Bidirectional Configuration: Peering is configured independently on each VNet. For two-way connectivity, create the corresponding peering in both VNets.
  • Allow virtual network access: Controls whether resources in the peered VNet can communicate using the peering connection.
  • Allow forwarded traffic: Allows traffic forwarded by a network virtual appliance or other routing device to cross the peering.
  • Allow gateway transit: Configured on the VNet that owns the VPN/ExpressRoute gateway so a peered VNet can use that gateway.
  • Use remote gateways: Configured on the peered VNet that wants to use the remote VNet's VPN/ExpressRoute gateway. A VNet using a remote gateway cannot also have its own gateway.

Azure Bastion

Fully managed PaaS providing browser-based RDP/SSH access to VMs without requiring a public IP address on the target VM. Bastion provides the secure access path while the VM can remain on a private IP.

Service Endpoints vs Private Endpoints

Both keep supported Azure service traffic on the Microsoft backbone, but they use different access models: Service Endpoints secure a PaaS service to selected VNet subnets, while Private Endpoints provide a private IP in your VNet for a specific supported resource.

Feature Service Endpoint Private Endpoint
IP Address The service continues to use its normal service endpoint/public DNS model; service traffic from the enabled subnet uses the Azure backbone and the subnet's private address space as the source identity. Creates a network interface with a private IP address in your VNet. Clients connect to the service through that private IP.
Access Model Extends the identity of the VNet/subnet to the supported Azure service. Provides private connectivity to a specific Azure resource through a private endpoint in your VNet.
On-Premises Access Not the mechanism for providing private on-premises access to the PaaS service. Can be reached from on-premises over VPN or ExpressRoute when routing and DNS are configured correctly.
Resource Scope Controls access to a supported service from selected VNets/subnets. Connects to a specific supported resource/subresource through a private IP.
DNS Normally uses the service's existing DNS name; no private endpoint DNS record is required. DNS must resolve the service FQDN to the private endpoint IP. Private DNS Zones are commonly used for this.
Cost No additional service-endpoint charge. Private Endpoint incurs applicable private endpoint and data-processing charges.
Exam Tip: Think Service Endpoint = subnet/VNet identity to a PaaS service and Private Endpoint = private IP in your VNet for a specific PaaS resource. Choose Private Endpoint when the requirement is private IP connectivity, private DNS resolution, or private access from on-premises through VPN/ExpressRoute.

Azure DNS

Azure DNS hosts DNS domains and provides name resolution using Microsoft's global network of name servers.

Zone Types

  • Public DNS Zone: Resolves domain names accessible from the internet (e.g. contoso.com).
  • Private DNS Zone: Resolves private DNS names for linked VNets and is not publicly resolvable. Auto-registration is an optional VNet-link setting that can automatically register VM records.

Common Record Types

Record Type Purpose
A Maps a hostname to an IPv4 address.
AAAA Maps a hostname to an IPv6 address.
CNAME Maps an alias hostname to another hostname.
MX Directs mail to mail servers.
TXT Holds arbitrary text, often used for domain verification (e.g. SPF).
NS / SOA Name server delegation and zone authority information (auto-created with the zone).
Virtual Network Links: A Private DNS Zone must be linked to each VNet that should use it for resolution. Auto-registration is optional; when enabled on a VNet link, supported VM records can be automatically registered and removed. For Private Endpoints, configure the appropriate private DNS zone and records so the service FQDN resolves to the private endpoint IP.

Public vs Internal Load Balancer

  • Public Load Balancer: Frontend has a public IP and can load balance internet-facing traffic to the backend pool. It can also provide outbound connectivity depending on the configured outbound design.
  • Internal Load Balancer: Frontend uses a private IP from the VNet and load balances traffic privately between clients and backend resources. It can be accessed from peered VNets or on-premises when connectivity exists.

Health Probes

Health probes determine which backend instances are healthy and eligible to receive new traffic. Supported Standard Load Balancer probe protocols are TCP, HTTP, and HTTPS. Load Balancer health probes originate from 168.63.129.16; NSGs and guest OS firewalls must not block the required probe traffic.

Network Watcher & Troubleshooting

Azure Network Watcher provides tools to diagnose routing, NSG, connectivity, and packet-level problems in Azure VNets. Connection Monitor provides continuous connectivity monitoring between sources and destinations.

Tool Purpose
IP Flow Verify Checks whether a specific packet (source/destination IP, port, protocol) is allowed or denied by NSG rules to or from a VM.
Connection Troubleshoot Performs a point-in-time connectivity test between a source VM and a destination such as another VM, FQDN, URI, or IP address, reporting reachability, latency, and the hop where a failure occurs.
Connection Monitor Continuously monitors connectivity between configured sources and destinations and can track connectivity, latency, and packet-loss trends over time.
Next Hop Shows the next hop type and route a packet will take from a VM toward a destination IP — useful for verifying UDRs and routing behavior.
Effective Routes Displays the combined set of system routes, UDRs, and applicable gateway/BGP routes actually available to a NIC.
Effective Security Rules Displays the combined set of subnet and NIC-level NSG rules actually applied to a NIC.
NSG Flow Logs Provides network traffic flow information for NSG troubleshooting, auditing, and traffic analytics where configured and supported.
Packet Capture Captures packet-level traffic to or from a VM for deep inspection and troubleshooting.

Troubleshooting Load Balancers

  • Health probe status: Check backend health. A probe failure can remove an instance from the load-balancing rotation.
  • Probe traffic: Ensure NSGs and the guest OS firewall allow the Load Balancer health probe traffic from 168.63.129.16.
  • Client traffic: Confirm NSGs and guest OS firewall rules allow the required client-to-frontend/backend ports.
  • Backend pool config: Confirm VMs/VMSS are correctly associated with the backend pool and that the load-balancing rule uses the expected frontend/backend ports.
  • Routing: Check Effective Routes and UDRs if traffic reaches the frontend but does not reach the backend.
