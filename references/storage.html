3. Storage Redundancy & Encryption

Redundancy Options

  • Locally Redundant Storage (LRS): 3 synchronous copies within the primary region.
  • Zone-Redundant Storage (ZRS): 3 synchronous copies across Availability Zones in the primary region.
  • Geo-Redundant Storage (GRS): 3 copies in primary region, replicated asynchronously to secondary region.
  • Geo-Zone-Redundant Storage (GZRS): 3 copies across zones in primary, replicated asynchronously to secondary region.
  • RA-GRS / RA-GZRS: Provides read access to the secondary regional copy.

Storage Encryption

All storage accounts use Storage Service Encryption (SSE) for data at rest using 256-bit AES encryption with Microsoft-managed or customer-managed keys.

5. Configure Access to Storage

Storage Firewalls & Virtual Networks

By default, storage accounts accept traffic from any network. Restricting access uses the Networking blade with two main mechanisms:

  • IP-based rules: Allow specific public IP addresses or CIDR ranges.
  • Virtual network (VNet) service endpoints: Restrict access to selected subnets; traffic stays on the Microsoft backbone.
  • Private Endpoints: Assigns a private IP from your VNet to the storage account, fully removing it from public internet exposure.
  • Trusted Microsoft services exception: Lets select Azure services (e.g., Azure Backup, Azure Monitor) bypass the network rules even when set to deny.
Default action: When any network rule is configured, the default action becomes Deny — you must explicitly allow the networks/IPs you want to permit.

Shared Access Signature (SAS) Tokens

A SAS grants limited, time-bound access to storage resources without sharing account keys.

SAS Type Scope Authorized By
User Delegation SAS Blob storage only Microsoft Entra ID credentials (most secure option)
Service SAS A single service (Blob, Queue, Table, or File) Storage account key
Account SAS One or more services in the account Storage account key

Every SAS token encodes: permissions (read/write/delete/list, etc.), start & expiry time, allowed IP range, allowed protocol (HTTPS only vs HTTP/HTTPS), and a signature computed from the account key or user delegation key.

Stored Access Policies

A stored access policy is defined on the container, file share, queue, or table itself and groups together the start time, expiry time, and permissions for one or more service SAS tokens.

Because the policy lives server-side, you can modify or revoke access for all SAS tokens tied to it at any time — without regenerating the storage account keys (which would invalidate every SAS on the account).

Managing Access Keys

  • Each storage account has two 512-bit access keys (key1 and key2) that grant full administrative access to the account.
  • Two keys exist so you can rotate one while the other remains active, avoiding downtime for applications using connection strings.
  • Keys can be regenerated from the portal, CLI, or PowerShell; consider storing them in Azure Key Vault.
  • Best practice: prefer Microsoft Entra ID authorization or SAS tokens over distributing account keys directly.

Identity-Based Access for Azure Files

Azure Files supports identity-based authentication over SMB using Kerberos, in addition to the traditional storage account key.

  • On-premises Active Directory Domain Services (AD DS): Requires syncing identities to Microsoft Entra ID and domain-joining the storage account.
  • Microsoft Entra Domain Services: A managed domain that Azure file shares can be joined to directly.
  • Microsoft Entra Kerberos (Entra ID authentication): Enables hybrid identities to authenticate to Azure Files with Kerberos without requiring a domain controller.

Once identity-based auth is configured, share-level and directory/file-level (NTFS) permissions both apply — share-level via RBAC roles, and file/folder-level via standard Windows ACLs.

6. Managing Storage Accounts

Creating & Configuring Storage Accounts

Key settings chosen at creation time (some are changeable later, others are not):

  • Subscription / Resource group / Name / Region
  • Performance: Standard (HDD-backed) or Premium (SSD-backed) — cannot be changed after creation.
  • Redundancy: LRS, ZRS, GRS, GZRS, RA-GRS, RA-GZRS — can generally be changed later.
  • Account kind: General-purpose v2, BlockBlobStorage, FileStorage, or BlobStorage — cannot be changed after creation (except GPv1 → GPv2 upgrade).
  • Networking: Public endpoint (all/selected networks) or private endpoint.
  • Data protection: Soft delete, versioning, and change feed toggles.

Object Replication

Object replication asynchronously copies block blobs between a source and a destination storage account, driven by a replication policy and one or more rules.

  • Requirements: Both accounts must be General-purpose v2, and the source account must have blob versioning and change feed enabled.
  • Use cases: Minimize read latency by copying data closer to users, reduce cross-region compute/egress by keeping copies in each region, and maintain a copy for compliance or DR purposes.
  • Unlike GRS/RA-GRS (which replicate the whole account transparently for disaster recovery), object replication is selective (container/prefix scoped) and the copy is independently readable and writable.

7. Configuring Azure Files & Blob Storage

File Shares in Azure Storage

  • Created within a storage account; can use SMB or NFS protocol (NFS requires Premium FileStorage account + private endpoint/VNet).
  • Tiers: Transaction Optimized, Hot, and Cool (standard tier accounts); Premium file shares use provisioned IOPS/throughput.
  • Each share has a configurable quota (maximum size).

Containers in Blob Storage

Containers group blobs, similar to a directory. Public access level is set per container:

  • Private (no anonymous access): Default — access requires a key, SAS, or Entra ID authorization.
  • Blob: Anonymous read access to blobs only, not container listing.
  • Container: Anonymous read access to blobs and full container listing.

Configuring Storage Tiers

Access tiers (Hot, Cool, Cold, Archive — see comparison table above) can be set at the account level as a default, or overridden per-blob. Archive-tier blobs must be rehydrated (Standard or High priority) to Hot/Cool before they can be read.

Soft Delete for Blobs & Containers

  • Blob soft delete: Deleted or overwritten blobs are retained for a configurable period (1–365 days) and can be undeleted.
  • Container soft delete: Extends the same protection to entire deleted containers.
  • Both are enabled independently under the account's Data protection settings.

Snapshots & Soft Delete for Azure Files

  • Share snapshots: Point-in-time, read-only copies of an entire file share, useful for point-in-time restore of individual files.
  • Share soft delete: When a file share itself is deleted, it is retained (1–365 days, default 7) and can be restored before permanent removal.

Blob Lifecycle Management

A rule-based policy (JSON or portal UI) that automatically transitions or deletes blobs based on age and conditions, without custom code.

Typical rule: "If a blob hasn't been modified in 30 days, move it to Cool; after 90 days, move to Archive; after 365 days, delete it." Rules can be scoped by container name prefix or blob index tags.

Blob Versioning

  • When enabled, every time a blob is overwritten or deleted, Azure automatically keeps the previous state as a read-only version.
  • Versions are identified by a VersionId timestamp and can be listed, read, or promoted back to the current version.
  • Works alongside soft delete and lifecycle management rules (which can also expire old versions) to build a complete data-protection strategy.
